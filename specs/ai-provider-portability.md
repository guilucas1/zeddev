# AI Provider Portability

## Purpose

Ensures the underlying AI language model/provider that powers bot conversations can be changed without re-architecting the system, since AI providers, pricing, and capabilities change over time (JTBD6). This spec defines the observable outcome of provider-swappability; it does not prescribe how that swappability is implemented.

## Behavioral Requirements

- The system must allow the operator to change which AI provider/model powers bot conversations without modifying the application's behavior-defining code.
- The system must allow the operator to change which AI provider/model powers bot conversations without requiring a redeployment of the application beyond what a configuration change ordinarily triggers.
- The system must not have any client-facing behavior, client-configured content (persona, tone, business knowledge, rules — see sibling specs), or client-facing feature hard-coded to assume a specific AI provider or model.
- The system must continue to produce behaviorally consistent bot responses for a client's existing configuration (persona, tone, knowledge, rules) after the active AI provider/model is swapped, without requiring the client to reconfigure anything.
- The system must continue to support all client-facing conversation capabilities in use at the time of the swap (e.g., text conversation handling, image message understanding, voice message understanding, conversation memory, human handoff, fallback behavior) after an AI provider/model swap, subject only to the technical capabilities of the newly selected provider/model.
- The system must allow the operator to verify a new AI provider/model is working correctly before it fully replaces the previous one as the active provider for live client conversations.
- The system must allow the operator to revert to the previously active AI provider/model if a newly activated provider/model is found to be unsuitable.
- The system must not require the operator to renegotiate, redefine, or manually re-enter each client's existing persona, tone, business knowledge, or behavior rules configuration as a consequence of an AI provider/model swap.
- The system must isolate the impact of an AI provider/model swap to bot response generation — it must not require changes to tenant data isolation, WhatsApp connection, or other non-AI-generation system behavior.
- The system must apply the active AI provider/model selection platform-wide, as an operator-level configuration, unless and until a per-client provider/model selection capability is separately specified (see Open Questions).
- The system must make the currently active AI provider/model identifiable to the operator (e.g., which provider/model is presently generating responses), without exposing that identity to end-customers or requiring end-customer awareness of it.
- The system must not degrade or alter a client's bot's disclosed identity or disclosure behavior (see `bot-disclosure-setting.md`) as a result of an AI provider/model swap.

## Acceptance Criteria

- Given the platform is running with AI provider A active, When the operator changes the active AI provider/model to provider B through configuration, Then no application source code changes or code-level redeployment is required to complete the swap.
- Given a client has an existing persona, tone, business knowledge, and behavior rules configuration under provider A, When the operator swaps the active provider to provider B, Then the bot's responses to that client's end-customers continue to reflect the same configured persona, tone, business knowledge, and behavior rules without the client taking any action.
- Given a client's bot supports text, image, and voice message understanding under provider A, When the operator swaps to provider B that supports the same message types, Then all three message types continue to be handled correctly after the swap.
- Given the operator wants to try a new AI provider/model, When the operator activates it in a verification/testing capacity, Then the operator can confirm its behavior before it becomes the provider serving live client conversations.
- Given a new AI provider/model has been made fully active and is found to be unsuitable, When the operator reverts to the previously active provider/model, Then bot conversations resume being generated by the prior provider without loss of any client's persona/tone/knowledge/rules configuration.
- Given multiple client tenants are active on the platform, When the operator swaps the platform-wide active AI provider/model, Then the swap applies uniformly to all tenants' bots at once, and no tenant is left on a different provider than the others unless per-client provider selection has been explicitly enabled (see Open Questions).
- Given an AI provider/model swap has occurred, When an end-customer interacts with a client's bot, Then the end-customer observes no indication of which underlying AI provider is in use, and the bot's disclosed identity/disclosure behavior is unchanged.
- Given an AI provider/model swap has occurred, When the operator inspects platform configuration, Then the operator can determine which AI provider/model is currently active.

## Out of Scope

- Cost-consciousness and preference for lowest-cost/free-tier-viable AI providers — see `cost-efficient-operation.md`.
- The specific mechanism, abstraction, or integration pattern used to achieve provider-swappability — intentionally left to a later implementation/design phase.
- Naming or mandating any specific AI vendor or model — none is prescribed by this spec.
- Definition of persona, tone, business knowledge, and behavior rules configuration themselves — see `persona-and-tone-configuration.md`, `business-knowledge-configuration.md`, and `behavior-rules-configuration.md`.
- Text, image, and voice message handling mechanics themselves — see `text-conversation-handling.md`, `image-message-understanding.md`, and `voice-message-understanding.md`.
- Conversation memory mechanics — see `conversation-memory.md`.
- Human handoff and fallback response behavior mechanics — see `human-handoff.md` and `fallback-response-behavior.md`.
- Bot disclosure content/rules — see `bot-disclosure-setting.md`.
- Per-client (as opposed to platform-wide) AI provider/model selection — not committed to in this spec; noted as an open question below.
- Automated or AI-driven selection of which provider to use — this spec covers operator-initiated, configuration-based swapping only, not automatic provider selection or load-balancing across providers.
- Data portability of conversation history or business knowledge into a new provider's format — not addressed here.

## Open Questions / Assumptions

- Assumed provider/model selection is a platform-wide, operator-level configuration applying to all tenants uniformly, rather than a per-client setting, since the interview did not mandate per-client selection and a single operator managing multiple clients makes platform-wide control the simpler default. Per-client provider selection is not ruled out for the future but is not required by this spec.
- Assumed "behaviorally consistent" responses after a swap means the same configured persona/tone/knowledge/rules continue to be reflected in bot output, not that response wording must be identical across providers — different providers/models will naturally phrase responses differently; this spec requires configuration fidelity, not verbatim output equivalence.
- Assumed the system must support some way to validate a new provider before it fully takes over live traffic, based on general product-quality expectations, since the interview did not specify a staged-rollout or testing mechanism explicitly.
- Assumed "without re-architecting the system" implies swaps should not require code changes or application redeployment beyond a configuration change, but does not necessarily mean zero downtime or instantaneous cutover; specific cutover timing/continuity guarantees were not specified in the interview and are left open.
- Assumed capability gaps between an old and new provider (e.g., a new provider lacking voice understanding) are the operator's decision to accept, not something this spec requires the system to compensate for or block on.
